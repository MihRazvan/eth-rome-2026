# Arkiv for Review Pass

Review Pass should target Mission 02, Mission 03 and automatic Best Use consideration. It has no genuine former indexer to decommission. The useful Arkiv product is a public, independently queryable board of funded technical-review opportunities with client-owned discovery leases. Expiry removes an opportunity from discovery; it never cancels escrow or erases an accepted reviewer’s work.

Research observed 12 September 2026, against shared implementation base `4f0cc87b405b8522f59e4c14d87ea546e77a4858`. The recommendations below are implementation decisions, not evidence of completed missions. Current local pilot tests establish separate wallets and document delivery; this pass establishes public reads and a reconnecting subscription. No public entity was created, no sponsor was contacted and no submission was sent.

## Native expiry as a product feature

A client publishes a funded job’s public scope and chooses a discovery lease. The lease means “I am actively recruiting through this board.” A short demonstration lease is 30 blocks, nominally one minute; the Fuji acceptance window must extend beyond that lease so the two mechanisms can be distinguished. When the lease expires, the public board removes the opportunity and the client’s own-work view labels it “Discovery lease expired; funds remain in escrow.” The client may republish a fresh lease or use the escrow’s ordinary cancellation/refund rules. Accepted work remains visible regardless of Arkiv record retention.

This is a real use of native expiry: stale recruiting advertisements disappear without a cleanup service. It is not a security revocation primitive. Someone who saved the job ID can still interact with an otherwise valid Fuji escrow; the contract remains authoritative. Do not promise that disappearance makes saved data private or prevents all future contract acceptance.

The [live-events guide](https://docs.arkiv.network/typescript-sdk/live-events/) explicitly says natural expiry emits no event. SDK 0.8.1 has creation, patch, extension, transfer and deletion callbacks, but no expired callback. Subscribe to actual WSS `newHeads`; when a head reaches the earliest known expiry, issue the same bounded board query once and reconcile against the returned live entities. Never remove an opportunity solely because a browser countdown reached zero. On query failure retain an unavailable/stale status and disable the discovery action; do not report an empty successful board.

For Mission 02 evidence, serialize one fixed compound query and use exactly that query before and after expiry. Do not advance a `deadline > now` predicate between screenshots. Capture a successful create receipt, actual applied expiry, before/after heads and outputs, visible app change, and a trace showing no delete/cleanup/extension across the boundary. The old `assignment.ts` query changes its deadline argument; it remains useful logical-deadline filtering but cannot alone establish this mission.

Use `flags: { readonly: true, permissionlessExtension: false }` for immutable advertisement terms. Readonly does not prohibit deletion, ownership transfer or expiry extension; these SDK semantics are important. Disabled permissionless extension prevents strangers from keeping a stale lease alive, though its owner can renew before expiry. Verify the current owner against the onchain client and never imply the namespace authenticates a record.

## Live subscriptions and recovery

The installed SDK wraps viem `watchEvent` at Arkiv operation address `0x4400000000000000000000000000000000000044`. Its event callback contains metadata, not query attributes or payload. A subscription cannot invent server-side filtering by qualification class. Use known-owner/key checks as preliminary relevance filters, then bounded event-triggered entity hydration and strict payload/authority validation. Event-driven HTTP reads are reasonable; periodic entity-query refresh loops are not Mission 03.

Construct a dedicated `createPublicClient({chain:tiramisu,transport:webSocket(wsUrl)})`. Call `watchEntityEvents` without `fromBlock`. In inspected viem source, any bigint `fromBlock` selects polling even when the transport is WSS; HTTP also selects polling. SDK `pollingInterval` does not turn an HTTP client into a socket. Subscribe separately to `watchBlockNumber({poll:false,...})` for expiry observation.

Install the stream before initial snapshot hydration, coalesce updates while hydration is pending, and requery once if anything relevant arrived during that read. Bound pending keys, payload size and concurrent hydrations; a noisy public database must not create unlimited requests. On disconnect, mark board state stale. Reconnect restores subscriptions, but missed events are not replayed. After a resumed head, perform a fresh bounded full query to reconcile current live advertisements; do not put `fromBlock` on the live watcher. If detailed historical replay is ever necessary, make it a separately bounded `getLogs` operation with deduplication. This board needs correct current state rather than an exactly-once history.

Use generation checks to prevent stopped or replaced subscriptions from repainting old UI. Deduplicate callbacks by block/transaction/log position and job identity. A deleted or already expired entity may be missing when its event is hydrated; handle that as a valid race. Test two genuine application clients with relevant and irrelevant writes, actual network trace, disconnect, recovery and unmount cleanup. The read-only public probe here is transport evidence only, not that two-client mission demonstration.

## Query model and authority

Use lowercase attribute names and a new schema version. Current MCP guidance records SDK/node disagreement for uppercase user attributes; the old camelCase query’s empty result is not a positive write control. Suggested attributes: `application`, `schema`, `kind`, `taskclass`, `qualificationclass`, `settlementchain`, `escrow`, `jobid`, `paymenttoken`, `reward`, `acceptbefore`. Store `reward` as `u256` base units, `acceptbefore` as `u64` Unix seconds, class as canonical uint32 decimal string, and addresses as normalized lowercase strings. Match types in query predicates. Include application/deployment namespace, kind, schema, class, chain and escrow; optionally reward range and token when they support a genuine user filter.

Keep title, short scope description, content reference and SHA-256 in a small bounded JSON payload. Public scope bytes belong on Swarm; confidential reports stay encrypted there. Do not call the public scope `encryptedBrief`. Bind the public scope reference/digest into the terms that the Fuji contract authenticates. No holder secret, credential ID, revocation index, assessment result, report plaintext, encryption private key or non-public contact detail belongs in attributes/payloads.

Select key, owner, creator, expiresAt, flags, attributes and bounded payload. Fetch every page before reporting a complete set; SDK page maximum is 200 and local use of 100 is reasonable. SDK user attributes max32, strings max128UTF-8bytes, payload max128KiB; Review Pass should impose tighter practical limits. Sorting one page does not establish a global best reward. There is no supported arbitrary server sort in the inspected 0.8 API.

Validate the advertisement against the configured Fuji contract before showing it actionable: chain, escrow, Open state, client/owner identity, funded reward/token/class/deadline and terms reference/digest. Arkiv signing alone authenticates its entity owner, not the escrow claim. Validate before deduplication so an attacker’s first duplicate cannot suppress the authentic job. Query failure and chain-verification failure must not trigger fixture fallback. Discovery never reserves a job; accept rechecks the contract.

## Public implementations and reusable guidance

The [official SDK repository](https://github.com/Arkiv-Network/arkiv-sdk-js) includes `sample/read_example.ts`, `write_example.ts` and `events_example.ts`. Use those to understand API shape, then inspect exact installed release behavior. Existing sample/history pages still expose older network/version examples. The current [query guide](https://docs.arkiv.network/typescript-sdk/querying-data/) and [fundamentals](https://docs.arkiv.network/start-here/fundamentals/) are better first references for new Tiramisu data models. Do not import all methods just because helpers exist: source guidance records unsupported node operators and expression/type differences.

The [official skills collection](https://github.com/Arkiv-Network/skills), inspected at `afce96c133276d4195f659b98a1b4d0ba2f0a86a` dated September9, provides best-practices and feedback workflows. Its namespace, typed-data, trust and pagination guidance is useful. Its prose still recommends dev because latest was0.7, and example `i32(Date.now())` exceeds int32. Treat those as genuine documentation friction; adapt them to the tested stable release and explicit `u64` seconds. Do not install/run a feedback workflow that publishes an issue: this task has no third-party outreach authorization.

The [official hub MCP](https://arkiv-mcp-gateway.vercel.app/ethrome) responded without a wallet or secret as server `arkiv-ethrome`1.0.23. Read-only initialization/catalog retrieval found15tools and289resources. It distinguishes current, historical and mixed guidance; its SDK corpus targets0.8.0 rather than our0.8.1. `guides/events-and-expiration`, `guides/skill-errata`, `guides/network-limits`, and `guides/ethrome-current` are relevant selective reads. PostgreSQL conversion, encrypted-entity wrappers and chunking are unnecessary for this product. Existing HPKE and Swarm boundary should not be replaced merely to add another package. Catalog receipts and provenance are retained without whole-source copies.

The sponsor’s [Puna Tech results repository](https://github.com/Arkiv-Network/arkiv-puna-tech-hackathon) lists prior winning implementations. [Susurro](https://github.com/artugrande/susurro) combines private client-side content, an expiring access workflow and a clear end-user demo. [LicitaVerify](https://github.com/hallzyx/licita-verify) turns procurement state into queryable evidence. Both are useful product references, but their READMEs target older Braga SDK versions. Their privacy/immutability claims are not independently verified here. Review Pass should borrow task clarity and evidence presentation, not copy old crypto/key derivation or network code. No existing repo discovered establishes that our combination is unique or guarantees a prize.

## Integration decision

Keep Arkiv SDK0.8.1 and viem2.56.3. Implement a new typed listings module under the pilot rather than silently mutate the old experimental schema. Make native recruiting lease expiry visible and useful, add true WSS updates with bounded recovery, and keep own escrow work sourced from Fuji. Finish these public features before accumulating more sponsor logos. Detailed function boundaries and tests are in `implementation.md`; public funding, write receipts, deployed frontend and actual two-client stream evidence remain release gates.
