# Frontier research for a product pivot

Research date: 12 September 2026, Europe/Bucharest. Window: **12 July–12 September 2026**. Independent worktree base: `920d66d45bfa1843f429a5f473a133cf863820d6`. This is a skeptical candidate screen, not implementation or demand validation. The newer pivot instruction supersedes the earlier EXIT product direction for this research; no historical acceptance evidence is changed.

**The strongest finding is negative: a generic agent wallet, delegated authority firewall, provenance receipt, shared memory store, or onchain license is already crowded.** Recent papers are useful building blocks, but reproducing their mechanism with sponsor storage does not establish novelty. Of the eight candidates below, cross-operator recovery and private qualification offer the clearest bounded demonstrations; neither yet has enough demand evidence to recommend an unconditional build. Memory recall is technically compelling but substantially less novel after the second prior-art pass.

Publication dates below come from publisher headings, arXiv submission histories, or GitHub release/merge metadata. `frontier-probes/date_check.py` independently fetched eight arXiv metadata pages and two GitHub API objects: all ten returned HTTP 200. The saved JSON contains observed metadata, not copies of papers. No paper benchmark, credential prover, enclave, sponsor integration, or product flow was executed in this research.

**1. Cross-operator recovery for one paid business operation — strongest demonstrability, moderate product novelty.**

The customer is a small team whose agent or automation provider dies during a paid job. The frightening state is “payment may have happened, but the provider lost the answer.” A portable recovery capsule binds a user-approved business-effect identifier, input commitment, completed steps, output references and contract transaction. A replacement operator decrypts that capsule and finishes the job without repaying the same obligation.

The live demonstration kills operator A immediately after its Fuji payment is included but before it acknowledges completion. Its Arkiv availability lease expires. Operator B discovers the orphaned job, retrieves the encrypted Swarm capsule, reads the consumed effect identifier from Fuji, and completes the remaining verifiable step. Show one actual token transfer despite retries and two different operators. A stale operator waking up later must also fail to duplicate the payment.

This is not “exactly once agents.” [Restate already journals work and skips completed payment steps on replay](https://docs.restate.dev/foundations/key-concepts); OpenClaw already consumes exact approved proposals. The possible contribution is recovery across independent operators without carrying the original service database or handing over a wallet key. A single onchain effect is enforceable; arbitrary bank, email or merchant side effects are not. A Swarm checkpoint proves only the committed bytes, not that a claimed offchain step happened. Recent agent-commerce adoption motivates the workflow, but idempotency is old. ENSv2 could govern independent recovery operators; it must not be presented as atomic authority over Fuji without an explicit crosschain trust mechanism.

**2. Private qualification for a paid, temporary assignment — strongest privacy mechanism, highest integration uncertainty.**

A worker or service provider needs to demonstrate that an issuer's qualification is currently valid without exposing a reusable credential identifier to every prospective customer. The application checks a challenge-bound non-revocation proof against a fresh issuer root, then creates a scoped work agreement with a Fuji refundable deposit. A credential holder can keep the full document encrypted on Swarm; expiring assignment availability belongs in Arkiv. ENSv2 issuer roles and resolver records are useful only if they participate in authenticating the actual issuer and root.

Demonstrate valid, revoked, stale-root and replayed presentations; two customers should see different presentation transcripts. The payment should depend on an actual verification result. [ShadowPath](https://arxiv.org/abs/2608.19937) is recent, but anonymous credentials and private revocation are established research areas; [USENIX 2026 private record certification](https://www.usenix.org/conference/usenixsecurity26/presentation/edalatnejad) is especially close. The distinguishing product must be an assignment workflow, not a renamed credential wallet. Issuer/verifier collusion, network metadata, and linkable wallet payments can defeat the wider privacy story. A self-issued demo credential is acceptable test data, but cannot be called real professional qualification. First gate: locate and run the actual proof code and verify the intended contract-compatible relation before designing the app around it.

**3. Source recall for shared agent memory — useful, substantially overlapping prior art.**

A team discovers that an internal source was wrong or compromised. Deleting its original record is insufficient if three summaries and a procedure were derived from it. The proposed recall room visualizes the explicit dependency graph, quarantines descendants for future execution, preserves unrelated sources, and lets a reviewer rebuild affected artifacts from clean evidence. Its demonstration should show a contaminated action before recall, an independently usable unaffected memory, and a blocked descendant afterward.

MAP-Graph already models ancestry and excludes permission-ineligible or revoked records. PPMF already addresses source-authority laundering. Tencent ships shared memory; [MemGuard's repository](https://github.com/ac12644/MemGuard) advertises quarantine and audit trails. [Arkiv's August ideathon](https://ideathon.arkiv.network/) includes ArcContext, a provenance-checked company memory idea; CausalGraph is construction evidence rather than this exact workflow. A clean recall UX could still help, but no mechanism novelty is established. Explicitly recorded lineage is enforceable; a model can omit a semantic dependency. The system cannot prove that a model has forgotten or that someone who downloaded plaintext can no longer use it. Arkiv expiry removes discoverability, not confidential history. Swarm portability is meaningful; a token payment is optional and likely decorative.

**4. Shared agent room with per-recipient information compartments — important problem, already an active product/research area.**

Two people collaborate with one agent, but Alice's private budget must not leak into Bob's answer or into a shared cached summary. Build separate inference contexts and explicit artifact access labels, with an owner-controlled disclosure action. Show Bob's transcript before and after Alice deliberately shares one datum; revoke a role and inspect that later retrieval and delivery stop. The boundary must be enforced in deterministic context construction and artifact delivery, not a prompt telling the model to keep secrets.

Cloudflare identifies the multi-principal problem, but that statement is not proof nobody addresses it. [AWS's 19 August AgentCore article](https://aws.amazon.com/blogs/security/propagate-user-authorization-context-in-ai-agents-with-amazon-bedrock-agentcore/) supplies infrastructure-enforced authorization-context patterns. MAP-Graph covers derived ancestry; Tencent and older collaborative-memory work are close. An ENS-governed room across independent providers is a possible product distinction, but storing private content in a decentralized service does not itself solve confidentiality. Swarm recipient encryption and Arkiv short-lived participation make sense. Forcing Fuji into every conversation weakens this idea.

**5. Graph-aware contractor removal — strong control demo, weak invention claim.**

An agency lends one worker to two client projects. Removing one subcontractor relationship should terminate that project's derived authority while retaining the independently authorized second project. Show two real permitted actions, remove one delegation edge, then demonstrate one blocked and one still working. The source of each permission should be visible so an administrator can understand the effect before revoking it.

VERA formalizes this distinction; [Arkiv Airlock](https://ideathon.arkiv.network/) already proposes expiring delegation chains with transitive revocation. The possible improvement over a tree is preserving independent paths, but that is the paper's contribution. ENSv2's hierarchy and account roles are a natural integration; dynamic graph policy may need a custom registry or resolver rather than simply nesting names. Arkiv can index live leases, but a lease's disappearance cannot secure an unchecked downstream action. Test stale cache, concurrent revocation and alternate-path preservation. A narrow contractor product is credible; a universal agent permission protocol would repeat existing work and oversell enforcement.

**6. Human intent versus final checkout — real failure, already-fixed core primitive.**

A human authorizes an exact invoice recipient, item, amount, network and deadline. An agent then encounters malicious merchant text that suggests a different recipient or substitutes an item. The app displays the exact difference and refuses to execute changed bytes without a new approval. A valid unchanged invoice still settles on Fuji, so the demo contains a positive control rather than only blocked attacks.

Beyond the Mandate motivates checking how an approved artifact was formed, but the system cannot decide whether an untrusted merchant's original description was true. OpenClaw's merged August 5 fix already freezes and consumes approved operations; Bounded Agents and Cloudflare cover external enforcement. The IETF draft distinguishes authorization registration from evidence of actual enforcement. A new approval ledger or “AI firewall” is therefore not enough. Potential product novelty would require one neglected checkout channel with genuine user evidence. Swarm receipts and Arkiv pending approval expiry fit, but neither authenticates a seller by itself. ENS can authenticate a controlled merchant identity, not establish that all products it advertises are legitimate.

**7. Portable proof of purchase from an existing website — recent enabling infrastructure, dependency and trust risk.**

A person needs to prove a narrow purchase fact to claim a refund, warranty or benefit without forwarding an entire account history. A user-controlled browser session produces a scoped attested statement; a counterparty verifies the fact and issues a testnet benefit. The dramatic demonstration is a genuine authorized website session, redacted minimum fields, independent verification, and rejection of a modified amount. If no real supported provider exists, stop at that concrete blocker rather than forging a portal and calling it a live integration.

Reclaim's August 9 Popcorn announcement makes browser handoff a timely enabler, but Reclaim already sells website-derived proofs. Its [public repository](https://github.com/reclaimprotocol/popcorn-oss) identifies browser runtime infrastructure; this review did not find or execute a complete local attestation path. Ordinary Docker isolation is not a TEE. A website proof does not transfer refund rights or prevent a second refund elsewhere. Swarm can preserve a portable encrypted evidence bundle and ENS can authenticate a benefit issuer; Fuji can enforce one redemption inside this application only. This should advance only after selecting an actual benefit with a unique redemption authority, not a generic “zk receipts” pitch.

**8. Commercial audio provenance plus scoped license — accessible demo, crowded and semantically weak.**

A small creative team needs a verifiable record of who supplied an audio asset and what use they authorized. The demo could verify an available provenance signal, obtain an explicit signed license from an ENS-authenticated issuer, pay test tokens, retrieve the encrypted master on Swarm, and independently inspect the permission terms. Arkiv can expose limited-duration offers without pretending the underlying asset disappears.

[OpenAI's provenance article](https://openai.com/index/advancing-content-provenance/) was originally published outside the requested window; its **31 July update**, concerning expanded audio watermarking and verification, is the recent event. It must not be relabeled a July original publication. [Story already provides licensing, royalty and dispute modules](https://docs.story.foundation/) and an agent commerce direction. Provenance establishes origin assertions, not truth, copyright ownership or enforceable control over every downloaded copy. This candidate is a low-priority fallback unless interviews reveal a specific licensing handoff that existing tools fail to complete.

**Sponsor fit and selection gates**

The supplied bounty file is the qualification source. Arkiv's strongest contribution is discoverable live state with native expiry and a real WebSocket event path; HTTP SDK polling is not WebSocket evidence. Use the same query before and after expiry, and do not add a deletion job to simulate it. Swarm needs real encrypted upload and retrieval that survive loss of the original application server. A hash of private low-entropy data can still reveal guesses; use encrypted objects or properly randomized commitments, and avoid putting content-derived secrets in query attributes.

ENSv2 must participate in authorization or programmable names on the official Sepolia beta. Fuji funds and rights live on another chain. A direct RPC observation of ENS state is an application trust decision, not a cryptographic crosschain proof. Either keep these authorities separate and explain them, or implement and test the synchronization assumption. Team1 needs an actual complete Fuji payment/rights flow, with only test assets; four sponsor logos do not compensate for a contrived payment.

Before choosing: require one concrete buyer/user problem; a working probe of the hardest new primitive; a precise comparison to the closest existing product; and a live positive/negative demonstration with independently inspectable outcomes. This research found useful ingredients and several compelling demonstrations, **but did not establish an uncontested novel product or prove demand**. The integrator should compare these findings against the other research streams rather than defaulting to the least-rejected item here.
