# Agent workflows and reusable skills

EXIT benefits most from narrow implementation ownership, independent reproduction and evidence that can survive a restart. A larger agent framework would add coordination work without resolving the product's current constraints. The useful next investment is a small project workflow that exercises actual wallet, chain and storage boundaries, with a read-only readiness command for live resources.

## What the evidence supports

Current official Codex documentation describes subagents as useful for separable exploration, tests and triage, while warning that parallel writers require care. Its skill model supports repository-scoped instructions and progressive loading. Those capabilities already exist in this environment; there is no requirement to install an additional orchestration runtime to use them. The relevant improvement is specifying the shared base, ownership, artifacts and integration gates precisely. [OpenAI, Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [OpenAI, Build skills](https://learn.chatgpt.com/docs/build-skills).

Anthropic's research-system account reports better breadth-first research results with an orchestrator and workers, but also considerable token consumption. The often-repeated 15× comparison in that article is against chat interactions, not a universal 15× multiplier over an equivalent single-agent coding task. Its internal research evaluation does not establish an expected productivity gain for EXIT. Independent research lanes make sense here because market mechanisms, browser experience and privacy threats have different sources and can return compact findings. [Anthropic, How we built our multi-agent research system, June 13, 2025](https://www.anthropic.com/engineering/multi-agent-research-system).

The MAST paper's revised version organizes agent failures around system design, inter-agent alignment and verification/termination. That is a useful diagnostic vocabulary, rather than a prediction that an arbitrary percentage of EXIT's work will fail. Its annotated systems and tasks are not this application's acceptance suite. A concrete adaptation is to require a reproduction or observable artifact with a finding, then have the integrator verify the combined branch. [Cemri et al., Why Do Multi-Agent LLM Systems Fail?, v3, October 26, 2025](https://arxiv.org/abs/2503.13657v3).

Productivity claims deserve the same skepticism as yield claims. METR's July 2025 randomized study found a 19% slowdown in its particular sample of 16 experienced open-source developers and 246 tasks. That result is not a timeless verdict about coding agents. Its February 2026 update says the newer experiment has serious selection and measurement problems, including difficulty measuring concurrent-agent work; it provides weak evidence about the size of current effects. The May 2026 survey is explicitly self-reported. These sources support measuring accepted outcomes and rework here, not using commit count, generated lines or promotional speedup claims as success metrics. [METR, July 10, 2025 study](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/), [METR, February 24, 2026 update](https://metr.org/blog/2026-02-24-uplift-update/), [METR, May 11, 2026 survey](https://metr.org/blog/2026-05-11-ai-usage-survey/).

## Orchestration choices

The operating unit should be an acceptance outcome. A task such as “make private offers secure” is too broad for isolated completion claims. A better task states the observed failure, the allowed code boundary, the actors, the data that must remain private and the evidence required to close it. Review should include effects outside the immediately changed module: exact-price token approvals were a public side channel despite correctly encrypted upload bytes.

Keep a single owner for integration, deployment manifests, shared quote formats and dependency changes. Parallel research can examine alternatives freely; parallel implementation should use explicit worktrees from the same committed base. A worktree separates files, not Anvil state, wallet nonces, databases, ports or cloud accounts. Browser workers should use separate contexts and explicit service ownership. Destructive teardown cannot infer ownership from a familiar port number.

Current Claude worktree documentation illustrates why runtime details must be checked rather than remembered. It distinguishes file isolation, hooks, inherited configuration, ignored files and base-selection behavior. Its tool-specific enforcement is not automatically present in another runtime, so EXIT's explicit ownership rules remain necessary. [Anthropic, Run parallel sessions with worktrees](https://code.claude.com/docs/en/worktrees).

A reviewer should first reproduce the old behavior on the exact base, then convert the failure into a meaningful assertion against the fix. Preserve the original characterization as historical evidence, but do not keep expecting the vulnerability in the normal test suite. Reviews should focus on observable boundaries rather than agree with implementation comments. In this round, independent probes used real HPKE and signatures to expose cross-wallet plaintext display; controlled networking supplied reproducible scheduling rather than simulated success.

## Evidence that deserves automation

Automate deterministic observations: chain IDs, public address code, signer separation, balances, test results and exact remote commit status. Keep interpreted conclusions explicit. A nonzero AVAX balance is not proven adequate deployment gas. A valid postage identifier is not proof that the gateway will accept it. An Arkiv read is not publication or native-expiry evidence. The new preflight command therefore cannot return a fully verified live product merely because configuration is present.

Use a small independent evaluation set derived from product failures. Useful cases include wallet changes while decrypting, an index outage while a claim is collectible, an incomplete HTTP request ahead of a real maker request, loss of the server's public-key certificate cache, private approvals visible to an outsider, and browser Back/Forward during a confidential negotiation. The test should assert the actual boundary, not count calls to an implementation helper.

Anthropic's long-running-agent work supports durable feature/progress artifacts and verification between sessions. Its application-harness account also describes separating the builder from browser evaluation. Those are relevant patterns, but their reported internal throughput or aesthetic results are not evidence of EXIT's quality. Here the useful record is a concrete failure, patch, command and resulting ownership/balance or visible-browser assertion. [Effective harnesses, November 26, 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [Harness design for long-running applications, March 24, 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps).

## Forum and social evidence

Community discussion can reveal failure hypotheses. It cannot establish current tooling behavior or economic safety by itself. A search-indexed Reddit discussion of agent handoffs highlighted stale shared records and reconciliation as an operational concern; this was retained only as an anecdotal lead, not a measured failure rate or independently verified incident. The underlying primary study and EXIT's own Git/chain checks provide stronger evidence for decisions. [Firsthand community discussion](https://www.reddit.com/r/AI_Agents/comments/1ulcleg/in_practice_our_multiagent_failures_were_almost/).

X searches surfaced promotional threads about parallel worktrees and underused agent features. Direct retrieval of the inspected post failed, so no claimed benchmark, capability or quotation from it is used as evidence. The referenced official documentation was inspected instead. This is an access limitation, not an inference that no useful practitioner material exists on X.

## Practical next direction

Keep the development loop small enough to inspect. Use the new readiness command when resources arrive, then exercise the actual Fuji/Arkiv/Swarm path and record real identifiers. Expand the reusable skill only when another repeated failure demonstrates missing guidance. Do not add autonomous public messaging, global hooks, speculative pricing agents or a new agent framework to make the tool list more impressive. The product's advantage comes from understandable rights, credible execution and a workflow that remains useful when one service fails.
