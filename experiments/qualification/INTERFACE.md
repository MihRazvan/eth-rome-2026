# Qualification proof interface — initial integration contract

Use Groth16 over BN254 and export a Solidity verifier with gnark's supported export. Prover worker must return exact ABI, public-input order and reproducible proof fixtures generated by real proving, with test keys explicitly labeled. No pretend proof or mocked verifier may substitute in integrated acceptance tests.

Proposed ordered public inputs, all BN254 scalar elements:

0. issuer EdDSA public key X
1. issuer EdDSA public key Y
2. current revocation Merkle root
3. required qualification class
4. proof validity deadline (bounded unsigned timestamp)
5. job context: keccak256 of ABI-encoded domain, chain ID, assignment contract, job ID, reduced modulo scalar field
6. recipient (Ethereum address as uint160)
7. job-scoped nullifier
8. presentation tag binding holder secret, context, recipient and validity deadline

Private witness: issuer signature over a domain-separated credential containing holder-secret commitment, revocation index, qualification class and credential expiry; holder secret; credential fields; Merkle authentication path. Prove signature authenticity, knowledge of holder secret, exact class, credential expiry >= proof deadline, and a non-revoked leaf at the SAME signed index. Bound integers and path indices. A depth-16 registry is an explicit prototype capacity, not a universal credential format.

Nullifier must be derived from holder secret + job context with its own domain. Do NOT include recipient/random presentation data in its derivation: that would allow a holder to change recipients to evade a per-job duplicate check. Presentation tag has its own domain and binds recipient/deadline to the witness. Define exact hashes/encoding in prover documentation before generating artifacts.

Contract independently checks issuer key/root against its own configured trusted issuer state, class against job requirements, current block time <= proof deadline, job context against this chain/contract/job, and recipient against the assignment beneficiary. Consume nullifier/assignment atomically with actual proof verification. A verifier-supplied stale root must not override configured current state. No ENS-to-Fuji authority is inferred.

Changes require a message to the integrator before consumers depend on them. Crypto worker should expose CLI commands for generating a local test credential/state and proving against caller-supplied context/recipient/deadline, alongside positive/negative tests. All proof artifacts must disclose setup trust and test-only issuer keys.
